# ACVP Primitive Validation

Continuous validation of this project's cryptographic primitives against
NIST CAVP-published test vectors and IETF RFC known-answer vectors, run
end-to-end on the shipping calculator binary via CEmu.

## What this is, and what this isn't

**This is**:

- An ongoing test that the AES-128-GCM, SHA-256, HMAC-SHA-256,
  HKDF-SHA-256, RSA-2048-PSS-SHA-256 verify, and X25519 (public key
  derivation + shared secret) primitives produce correct outputs for
  inputs taken directly from NIST CAVP archives and IETF RFC test sections.
- Random-sampled per CI run: on every push to `tls`, `tools/cavp_fetch.py`
  randomly samples 5 vectors per CAVP-covered algorithm. The seed is
  logged so any failing run can be reproduced (`CAVP_FETCH_SEED=<seed>`).
- For RSA-PSS, NIST publishes both positive (`Result = P`) and negative
  (`Result = F (...)`) vectors. The sampler guarantees at least one of
  each so a verifier that always accepts (or always rejects) is caught.
- A CI gate: any commit that breaks primitive correctness will fail
  `.github/workflows/acvp.yml`.

**Vector sources**:

| Primitive | Source | Type |
|---|---|---|
| AES-128-GCM | NIST CAVP `gcmEncryptExtIV128.rsp` | Sampled per run |
| SHA-256 | NIST CAVP `SHA256ShortMsg.rsp` | Sampled per run |
| HMAC-SHA-256 | NIST CAVP `HMAC.rsp` (L=32, Tlen=32) | Sampled per run |
| RSA-2048-PSS-SHA-256 verify | NIST CAVP `SigVerPSS_186-3.rsp` | Sampled per run |
| HKDF-SHA-256 | RFC 5869 §A.1-A.3 | Pinned (CAVP doesn't publish) |
| X25519 publickey | RFC 7748 §6.1 | Pinned (CAVP doesn't publish) |
| X25519 shared secret | RFC 7748 §5.2 + §6.1 | Pinned (CAVP doesn't publish) |

**DRBG is intentionally NOT included.** NIST CAVP Hash_DRBG vectors require
a deterministic `instantiate(entropy, nonce, personalization)` +
`generate(N, additional)` API. This project's DRBG seeds from the SRAM
entropy tap on a 50ms timer cycle and does not expose a deterministic
seed entry point. Until standalone `tls_drbg_instantiate /
tls_drbg_generate / tls_drbg_uninstantiate` functions exist, DRBG
validation lives under whitepaper §4.2 (NIST SP 800-90B entropy source
analysis) rather than under ACVP. The dispatcher in `src/main.c` retains
the DRBG slot as a stub so the wiring is ready when the API lands.

**This is not**:

- A NIST CAVP certificate. CAVP requires submission through an accredited
  lab. This project does not have, and does not claim to have, an issued
  CAVP cert. It is "validated against CAVP-published test vectors" —
  which is a strictly weaker claim, but is the strongest claim achievable
  without lab involvement.
- A FIPS 140-3 module validation. That would require submission through
  the CMVP, and is not feasible on consumer calculator hardware in any case.

For the project's full posture on cryptographic validation, see the
whitepaper.

## Files

```
tls_acvp/
├── README.md            (this file)
├── Makefile             (builds ACVPTEST.8xp)
├── autotest.json        (CEmu autotester sequence)
├── src/main.c           (calc-side runner: TLV dispatcher per algorithm)
├── vectors/             (all gitignored; populated by cavp_fetch.py)
│   ├── cache/           (cached NIST CAVP zip archives)
│   ├── ACVPIN.8xv       (packed input AppVar for the calc)
│   └── expected.json    (per-run grading source for the parser)
└── tools/
    ├── cavp_fetch.py        (single source of truth: fetch -> sample -> pack)
    └── parse_output_appvar.py (ACVPOUT.8xv -> graded pass/fail summary)
```

The `vectors/` directory is **entirely gitignored**. Nothing in it is
committed; both ACVPIN.8xv and expected.json are regenerated by
`cavp_fetch.py` on every CI run. The cached CAVP zips are kept across
runs (GitHub Actions cache) for bandwidth, but the random-sampled
vectors inside are fresh every time.

## Wire protocol (calc ↔ host)

**ACVPIN.8xv** (host-generated input):
```
magic[4]      = 'A','I','N','1'
vector_count  uint16  LE
repeat:
  algorithm_id  uint8   (1=AES-GCM, 2=SHA256, 3=HMAC, 4=HKDF, 5=DRBG,
                         6=RSA-PSS-VERIFY, 7=X25519-PUBKEY, 8=X25519-SECRET)
  test_id       uint16  LE  (opaque to calc; used to match responses)
  payload_len   uint16  LE
  payload[payload_len]   (algorithm-specific TLV, see src/main.c)
```

**ACVPOUT.8xv** (calc-generated response):
```
magic[4]      = 'A','O','U','T'
response_count uint16 LE
repeat:
  test_id      uint16  LE
  status       uint8   (0=ok, 1=unsupported, 2=internal_error)
  result_len   uint16  LE
  result[result_len]
```

The calc never sees expected outputs and cannot grade itself. Grading
happens host-side by comparing `result` against the per-test-id record
in `expected.json` (which was emitted by `cavp_fetch.py` alongside
`ACVPIN.8xv`).

## Local development

End-to-end run:

```sh
# Fetch CAVP archives, sample vectors, write ACVPIN.8xv + expected.json
python3 tools/cavp_fetch.py

# Build the calc-side runner
make clean all

# Run via CEmu autotester
make test

# Grade the resulting ACVPOUT.8xv
python3 tools/parse_output_appvar.py
```

To reproduce a specific CI run that failed:

```sh
CAVP_FETCH_SEED=1234567890 python3 tools/cavp_fetch.py
# ...then run the rest as above with the same vectors that failed in CI
```

To use a larger sample (default is 5 per CAVP primitive):

```sh
CAVP_FETCH_SAMPLE=20 python3 tools/cavp_fetch.py
```

## CI integration

`.github/workflows/acvp.yml` does, on every push to `tls`:

1. Install CEdev + build CEmu + autotester (cached).
2. **Cache** the NIST CAVP zip archives in `vectors/cache/`.
3. Run `cavp_fetch.py` to produce a fresh per-run `ACVPIN.8xv` +
   `expected.json` (with a fresh random seed, logged in the job output).
4. Build and run ACVPTEST.8xp under CEmu.
5. Run `parse_output_appvar.py` to grade ACVPOUT against expected.json
   and emit a markdown summary into the job step summary.

## Failure modes

| Symptom in CI | Likely cause |
|---|---|
| `ACVPOUT.8xv was not produced` | Calc-side runner crashed; check `autotest.log` artifact |
| Per-vector `fail: tag mismatch` (AES) | AES-GCM bug, or wrong vector wire encoding |
| Per-vector `fail: digest mismatch` (SHA/HMAC) | Hash bug |
| Per-vector `fail: okm mismatch` (HKDF) | HKDF extract/expand wiring bug |
| Per-vector `fail: pubkey mismatch` (X25519-PUBLICKEY) | X25519 base-point scalar mult bug |
| Per-vector `fail: shared secret mismatch` (X25519-SECRET) | X25519 scalar mult / point validation bug |
| RSA `fail: positive test: calc rejected but should have accepted` | RSA modexp or PSS decode bug |
| RSA `fail: negative test: calc accepted but should have rejected` | **Verify is broken in the dangerous direction.** Verifier accepting corrupted signatures means SPKI pinning gives no security. Investigate immediately. |
| Per-vector `unsupported` (DRBG) | Expected for now — DRBG standalone API not wired |
| `fail: no response received` for some test_id | Calc ran out of memory or skipped a vector |

When a failure happens, the workflow logs the `CAVP_FETCH_SEED` used.
Re-running with that seed locally reproduces the exact same vector set.
