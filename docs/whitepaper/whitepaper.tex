	\section{Foreword}

	\textbf{lwIP-CE} ports the Lightweight IP (lwIP) stack to the TI-84+ CE, bringing USB Ethernet, IPv4/IPv6, and TLS 1.3 to a 48 MHz, single-threaded platform with limited RAM and no native networking abstraction. The objective is not connectivity at any cost, but standards-aligned, interoperable networking within the calculator's hardware constraints.

	This whitepaper documents the resulting architecture, from USB transport and Ethernet abstraction through lwIP integration and TLS. It describes the memory model, resident-application interface, cryptographic components, validation strategy, and engineering trade-offs required to make contemporary secure networking practical on this platform. In doing so, lwIP-CE serves as both a usable networking stack and a proof of feasibility: deeply constrained systems need not abandon protocol correctness, clear architectural boundaries, or systematic testing.

	The document is intended for embedded-systems developers, networking and security engineers, auditors, and calculator developers. It assumes familiarity with TCP/IP, embedded software, and basic cryptographic concepts.

	I am mindful of the familiar warning, ``Don't roll your own crypto.'' Where mature, audited libraries are available, that advice is essential; the TI-84+ CE, however, has no such implementation suited to its ABI, memory limits, and performance envelope. CryptX began as a proof of concept and learning exercise, then matured as community interest and my own understanding grew. Extending that work into TLS 1.3 raised the standard considerably: ``good enough'' was no longer adequate, and design choices had to be grounded in protocol compliance, known-answer testing, statistical validation, and explicit documentation of platform trade-offs. This project is where I learned much of what I now know about cryptography, and that growth is reflected in its progression from experimentation toward disciplined security engineering.

	lwIP-CE targets conformance with the applicable RFCs and uses standardized cryptographic primitives and validation methods where practical. It is not a FIPS-validated cryptographic module and has not undergone an independent professional security audit. Review and validation to date include third-party calculator-community review, static application security testing, continuous-integration validation pipelines, and AI-assisted analysis using \texttt{Codex/Daybreak Blue}. Any security assurances should therefore be understood within that context.

	The platform necessarily imposes trade-offs among performance, memory use, and defensive hardening. This paper documents the cryptographic constructions, mitigations, limitations, and design rationale so that readers can evaluate those decisions on their merits.

	\subsection{Porting lwIP to the TI-84+ CE}
		The initial porting effort was undertaken by Cemetech user \textit{commandblockguy}, who prepared lwIP for the TI-84+ CE environment by isolating and conditionally excluding features incompatible with the calculator’s execution model. This included removing OS-dependent functionality, threading assumptions, and unsupported memory abstractions, while preserving protocol correctness.
		
		A more substantial challenge arose from the calculator’s atypical integer model. The eZ80 CPU operates in a 24-bit address and data environment, and under the CE toolchain, the fundamental C types differ from conventional 32- or 64-bit architectures. In particular:
		\begin{itemize}
		\item \texttt{short} is 16 bits
		\item \texttt{int} is 24 bits
		\item \texttt{long} is 32 bits (implemented as multi-register operations)
		\end{itemize}
		At the time of the original port, support for integer widths beyond 32 bits was limited, requiring careful handling of any operations that assumed native 32-bit promotion semantics. Arithmetic exceeding 24 bits incurs compiler-generated multi-register sequences, and operations beyond 32 bits required explicit multiprecision handling.
		
		Subsequent revisions of the toolchain introduced additional fixed-width types (e.g., 48-bit and 64-bit integers), allowing portions of earlier compatibility workarounds to be simplified or reverted. Nevertheless, all lwIP fixed-width types were explicitly audited to ensure that their effective widths and promotion behavior matched protocol expectations.
		
		\subsection{USB CDC-Class Ethernet driver}
		To provide reliable networking on TI-84+ CE hardware, a USB CDC Ethernet host driver was implemented for ECM (Ethernet Control Model) and NCM (Network Control Model) adapters. These are the common CDC Ethernet profiles available on commodity USB dongles and provide the broadest practical compatibility.

		The implementation is layered on \texttt{USBDRVCE}, the toolchain USB library by \textit{jacobly}. \texttt{USBDRVCE} owns low-level bus/device lifecycle handling; the CDC layer focuses on class parsing, endpoint wiring, and forwarding frames into lwIP.

		The driver lifecycle is summarized below. Discovery deliberately searches all configurations because vendor-specific interfaces commonly precede the usable CDC interface. NCM negotiation bounds the input NTB to approximately 2\,KiB, limiting burst memory on the calculator; ECM requires no equivalent aggregation step.

		Successful RX completions normally enter lwIP immediately and rearm the transfer in the same polling cycle. The overflow ring exists only for temporary pbuf exhaustion, and its drain timer stops once the queue is empty. A periodic dispatcher recovers transfers that fail to rearm; disconnects and unrecoverable stalls instead tear down device state and restart through the ordinary enable path.
		
		This driver provides platform-appropriate USB Ethernet transport for lwIP on TI-84+ CE hardware. Its focused CDC ECM/NCM support, direct RX delivery with immediate transfer rearming, bounded overflow buffering under memory pressure, and deterministic endpoint recovery provide stable link behavior within the platform's memory and timing constraints.
	
	\section{Architectural Considerations}

	\subsection{Application Callability}
	\label{ssec:application_callability}

		lwIP-CE is intended to operate similarly to a dylib for a conventional computer architecture that you would include via including definitions/fuctions from standard header, resulting in references to the library binary being linked into your code. I was intent on making this library callable in place rather than statically included because the lwIP core and TLS internals are huge (around 415 KiB) and on a device with just under 2 MiB of Flash storage, this adds up quickly.

		The toolchain utility \texttt{LIBLOAD} provides this dylib functionality loosely on the TI-84+ CE by building a relocatable symbol table that is patched in-place at initialization.

		A Flash Application, which this project needs to be, is unsupported by \texttt{LIBLOAD} for a handful of reasons. Standard LIBLOAD cannot directly support this resident Flash Application because Flash cannot be patched in place and the App’s writable runtime sections are not initialized when it is called without being launched normally.

		A solution was identified that involved using a LIBLOAD stub library that contains:
		
		\begin{itemize}
			\item A table of exports, initialized to a no-op function defined in the stub.
			\item A table of imports, zero initialized.
			\item A single initialization function that:
			\begin{itemize}
				\item Imports caller's CRT (malloc, free, realloc) and external dynamic dependencies into the stub's imports table.
				\item Locates the LWIP Flash Application, finds its exports table, validates the magic header, patches the stub's exports table to the correct in-Flash addresses.
				\item Calls a now-valid internal initialization function that causes the App to initialize its runtime by zeroing \texttt{.bss}, coping \texttt{.data} from Flash to RAM, and copying the imports table into place.
			\end{itemize}
			\end{itemize}

			\paragraph{Versioning \& Export ABI Compatibility}
			lwIP-CE releases are versioned in tuples, defined: \texttt{MAJ.MIN.PATCH}. The patch number will typically bump for bugfixes, RFC or other spec compliance patches, or periodic re-syncs with lwIP's upstream (the ported source). The minor version number will typically bump for smaller feature additions or algorithm additions. Forward compatibility is maintained through minor and revision updates. The major version number will bump for major API changes or massive functionality changes. While forward compatibility remains a goal, major releases may break forward-compat; Please check the release notes for indication of if a release affects compatibility.

			The LIBLOAD stub handles the following version (mis)matches:

			\begin{xltabular}{\textwidth}{@{}
				>{\raggedright\arraybackslash}X
				>{\raggedright\arraybackslash}X@{}}

				\toprule
				{Version pairing} & {Compatibility behavior} \\
				\midrule
				\endhead
				\bottomrule
				\endfoot

				Newer resident App with older companion stub & Startup succeeds and the shared export prefix is patched. APIs added after the stub was built are not exposed. \\

		\subsection{Membuffer "driver"}
		\label{ssec:membuffer}
		In addition to the USB driver, a dedicated \texttt{membuffer} layer was implemented that abstracts the caller's CRT into lwIP via pointers to \texttt{malloc}, \texttt{realloc}, and \texttt{free}. However, this implementation does far more.

		The abstraction allows you to create membuffer "objects" of varying types.

		From a security perspective, any buffer can be flagged with \texttt{BUFFER\_SECURE\_MODE} (always on for \texttt{MEM\_BUFFER\_FILE}), enabling automatic zeroization on pop, free, release, and destroy. This does not replace higher-layer cryptographic hygiene, but it reduces residual plaintext/key exposure in normal allocator lifecycles.

		Two further constraints govern, specifically, how decrypted TLS handshake plaintext moves through the allocator --- a narrower scope than general allocator usage, since the fixed pbuf pool and most other consumers are not held to these rules:

		\begin{itemize}
			\item \textbf{Single-copy rule.} At any point during handshake processing, each byte of handshake data exists in at most one heap buffer. For \texttt{Certificate} messages this means the cert walker's per-cert DER buffer is populated by consuming bytes from the decrypted record pbuf in-place; there is never a full copy of the certificate message sitting alongside the record scratch. For other cross-record handshake messages the reassembly buffer accumulates bytes that have already been consumed (and freed) from the record pbuf, so again at most one copy exists.
			\item \textbf{Chunk-copy rule.} Neither the cert walker nor the reassembly path reads the entire plaintext into a second large allocation before processing. The cert walker is fed segment-by-segment from the pbuf chain, accumulating only the bytes of the current certificate's DER. The reassembly buffer grows incrementally as each decrypted record segment is appended, freeing the record pbuf promptly after its bytes are copied in.
		\end{itemize}

		\subsection{Unified Event System and Diagnostic Traceback}

		Every module that can fail---USB, the custom allocator, TLS handshake/record processing, and the lwIP-CE glue layer itself---routes notable events through a single shared callback rather than each maintaining its own ad-hoc logging. The library performs no I/O of its own; if the caller wants a console, a persisted log, or an on-screen HUD, that happens inside the callback it registers with \texttt{lwip\_set\_event\_cb}. Each event carries a \texttt{module} (which subsystem) and a \texttt{kind}: \texttt{INFO} milestones, \texttt{DEBUG} trace points (self-throttling---a given \{file, line\} only re-fires once it stops repeating), \texttt{WARN} for tolerated problems, \texttt{ERROR} for hard failures, \texttt{STATE\_CHG} for transitions worth surfacing on their own (link up/down, IP acquired/lost, connection established/closed/failed, TLS handshake begin/done/failed), and \texttt{IO\_FILE}/\texttt{IO\_ETH} for AppVar and network byte-level traffic.

		On a single-threaded, callback-buried system like this one, the practical debugging problem is rarely ``something failed''---the application layer already gets that much from a socket error or a closed connection. The problem is finding \emph{where}, several callback frames removed from the code that can act on it, without re-running the failure under a debugger that may not even be attachable (most field failures happen on hardware, not in an emulator). To address this, every \texttt{WARN} and \texttt{ERROR} event additionally pushes a compact entry into a 32-deep ring buffer, independent of whether a callback is even registered. The application can pull this buffer at the moment it actually needs it---typically right after a socket operation reports failure---rather than having had to be watching every event live as it happened.

		\begin{verbatim}
const struct lwip_traceback_entry *lwip_get_traceback(uint8_t *count);
		\end{verbatim}

		Calling this returns a pointer to an internally-owned array (valid until the next call, or until another entry is pushed) ordered newest-first, along with how many entries it holds. A typical consumer walks it immediately after observing a failure:

		\begin{verbatim}
uint8_t count;
const struct lwip_traceback_entry *entries = lwip_get_traceback(&count);
for (uint8_t i = 0; i < count; i++) {
    const struct lwip_traceback_entry *e = &entries[i];
    printf("file=%s line=%lu err=%d\n",
           lwip_debug_file_name(e->file), e->line, e->raw_error);
}
		\end{verbatim}

		\begin{wrapfigure}{r}{0.42\linewidth}
			\centering
			\includegraphics[width=\linewidth]{traceback_demo.jpg}
			\caption{\footnotesize On-device traceback output from the browser example after a TLS fetch failure. The socket-level error appears first, followed by the stack frames that led to it.}
			\label{fig:traceback_demo}
		\end{wrapfigure}

		Two kinds of entry can appear in the buffer. A \emph{code} entry (an ordinary \texttt{WARN}/\texttt{ERROR} raised from inside the stack) carries \texttt{module}, \texttt{kind}, \texttt{file}, \texttt{line}, and an optional caller-supplied \texttt{extra} code identifying the exact source location and circumstance. A \emph{socket} entry, pushed by the higher-level socket wrapper API when it maps an internal failure into something the application sees, instead carries \texttt{component} and \texttt{operation} (which socket subsystem and call were involved), \texttt{raw\_error} (the underlying \texttt{err\_t} or module-specific code), \texttt{mapped\_error}, and \texttt{status}---\texttt{file}/\texttt{line} are zero on these, since the causal call site is expected to already be present as a preceding code entry in the same trace. In both cases the entry is small and fixed-size, so the whole buffer costs a bounded, constant amount of memory regardless of how chatty a given failure was.

		The result is that a socket-level failure---a connection that times out, a write that fails, a handshake that aborts---is no longer just a single opaque status code at the top of the call stack. The application can walk backward through exactly the chain of WARN/ERROR events that led to it, down to the file and line where the underlying condition was first detected, without needing to have instrumented anything in advance or reproduced the failure under a debugger.

		\section{TLS 1.3 Implementation Considerations}
	
	This section is not a full TLS implementation guide; it focuses only on platform-specific design choices and any standards deviations that require explicit justification.
	
	\subsection{Threat Model}
	
	lwIP-CE's TLS security claims are network-level claims made on top of commodity calculator hardware. The implementation is designed primarily to defend against remote network adversaries; it does not turn the TI-84+ CE into a trusted execution environment.
	
	\paragraph{Remote Adversaries}
	
	The primary threat model assumes a remote attacker capable of observing, intercepting, and modifying network traffic between the calculator and a remote endpoint. This includes:
	
	\begin{itemize}
		\item Passive network eavesdropping.
		\item Active man-in-the-middle (MITM) attacks.
		\item Malicious or compromised TLS servers.
		\item Malformed or adversarial network inputs intended to trigger parser or protocol failures.
	\end{itemize}
	
	Against this class of attacker, the implementation aims to provide confidentiality, integrity, endpoint authentication, robust parser behavior, and fail-closed handling for malformed protocol inputs, subject to the trust model and algorithm support described in this document.
	
	\paragraph{Local and Physical Adversaries}
	
	Local attackers are treated as a bounded-resistance case, not as a fully defended case. A user or tool with access to calculator storage or execution state may be able to:
	
	\begin{itemize}
		\item Replace application binaries or calculator variables (AppVars).
		\item Modify truststore data or configuration files.
		\item Inspect non-protected memory contents.
		\item Patch binaries or firmware outside the normal execution environment.
		\item Observe power, electromagnetic, or timing side channels during cryptographic operations.
	\end{itemize}
	
	The platform provides no secure storage primitive, protected execution environment, hardware root of trust, secure enclave, or tamper-resistant memory. Accordingly, protection against determined local compromise, physical device compromise, malicious firmware, and advanced side-channel analysis is outside the scope of this implementation. The memory-clearing and guarded-execution mitigations described later reduce residual exposure during normal operation but are not a substitute for secure hardware.
	
	\paragraph{Security Goals}
	
	Within those boundaries, lwIP-CE aims to provide:
	
	\begin{itemize}
		\item Standards-compliant TLS 1.3 handshakes.
		\item Protection of application data against passive and active network attackers.
		\item Robust parsing and rejection of malformed protocol inputs.
		\item Controlled handling of memory and sensitive state where feasible on the platform.
	\end{itemize}
	
	\subsection{Hardware Entropy Profiling and Conditioning}
	\label{ssec:hwrng_design}
	\label{sec:entropy}
	\label{ssec:entropy}
	
	Randomness is the foundational security dependency for the TLS stack; if the source is weak, all downstream cryptography is weakened regardless of algorithm choice.
	
	The first technical question, therefore, was whether the TI-84+ CE exposes usable entropy, and if so, how that entropy behaves across hardware revisions. Unlike general-purpose systems, the calculator has very few reliable entropy sources. Early candidates (such as the \texttt{r} register and cycle counters) were rejected as predictable. The investigation then shifted to hardware-level behavior in unmapped SRAM regions, using community discussion and direct measurement to build a source model that could be tested and bounded.

	This section documents the RNG design rationale and construction, including the statistical and mathematical basis for key decisions, explicit assumptions, identified failure modes, and bounded security estimates. It is not a claim of NIST SP 800-90* compliance or certification. Its purpose is to show that the design was developed against the NIST model and evaluated deliberately rather than implemented ad hoc.

	\paragraph{Entropy Characterization}
	Our investigation determined that the calculator does expose usable entropy, but through a much narrower and weaker physical mechanism than modern general-purpose systems: repeated reads from the calculator's unmapped SRAM address range. Cemetech user \textit{Zeroko} summarized the underlying behavior as follows:
	
	\begin{newquote}
		SRAM has a pair of bitlines for each bit of each column address, which are connected to a circuit that tries to make them both be charged to an equal, high level before reading from a memory cell (which partially discharges one of the two) and to a sense amplifier (basically a comparator) to read the resulting state afterward. (There may also be another level of gating between the bitlines and the comparators, but that does not strongly affect the dynamics.) In the unmapped space, there are no memory cells, so the controller equalizes the bitlines however well it does, then does nothing (there being no memory cell to discharge them), then senses which bitline is at a higher level. For some column addresses, this will be heavily biased one way or the other because the pre-charge transistors on the bitlines are too different, while for others, it will be less biased because they are more similar.\\\\
		Another source of non-randomness distinct from the bias is that the bitlines act like capacitors, so precharging only moves their voltage toward the desired level rather than reaching it. This results in a correlation between reads, with the correlation getting weaker with a longer time interval between them and with more intervening reads performed. This is why we cannot just use a von Neumann extractor (which only de-biases) and instead have to do something like XORing many consecutive bits together (which does not fully remove the bias and correlation but can lower it to an undetectable level).  \footnotemark
	\end{newquote}
	\footnotetext{https://www.cemetech.net/forum/viewtopic.php?p=293079\\\textit{Producing crypto-safe randomness on the TI-84+ CE.}}
	
	A clearer restatement followed later in SAX (Cemetech's built-in IRC-style chat room):
	\begin{newquote}
		The circuit involved [in generating entropy] is an SRAM sense amplifier connected to bit lines with no SRAM memory cells at the relevant addresses. So [the circuit] tries to equalize the voltage on the lines (but not quite due to thermal \& noise fluctuations) \& then uses a comparator to decide which is higher (also subject to noise near the decision boundary).
	\end{newquote}

	For readers with a computer engineering background, these mechanics are expected. The key constraint is that, unlike desktop or server platforms that combine many entropy inputs, this platform relies on a single dominant source region with two defining properties:
	\begin{itemize}
		\item Entropy introduced through noise 
		\item Bias and correlation introduced via lazy voltage balancing behavior by the controller
	\end{itemize}
	
	\paragraph{Entropy Tap Selection Model}
	The generator selects an entropy tap via the following algorithm:
	\begin{itemize}
		\item Scan all eight bit positions at each of the 513 byte addresses beginning at \texttt{0xD65800}. No acceptable early candidate terminates the scan.
		\item At each address, perform 256 pairs of physically adjacent reads, producing 512 marginal observations and 256 pairwise transition observations for every bit position.
		\item Require the marginal one-count to lie in $[128,384]$, equivalent to an observed $\hat p(1)\in[0.25,0.75]$ over the discovery sample.
		\item Require the adjacent-pair disagreement count to lie in $[64,192]$, rejecting both nearly static sources and sources dominated by deterministic alternation.
		\item Score each qualifying address/bit pair as $s=\min(d,256-d)$, where $d$ is its disagreement count. The candidate with the largest score---the transition rate closest to one half---becomes the primary tap; the first candidate wins an exact tie, making selection deterministic for a fixed observation sequence.
		\item Retain up to three eligible candidates displaced from the lead or tied with it as recovery candidates.
		\item After completing the scan, revalidate the selected tap using 512 fresh adjacent pairs (1,024 raw reads). Revalidation requires a marginal one-count in $[256,768]$ and a disagreement count in $[128,384]$; initialization fails if the selected tap does not pass this independent sample.
	\end{itemize}
	
		The following \textbf{derived assumptions} apply:
		\begin{itemize}
		\item The marginal and disagreement limits characterize only the finite discovery and revalidation samples. They do not prove independence or establish the source's future min-entropy rate.
		\item The disagreement score is a source-selection heuristic, not an entropy estimator. Min-entropy accounting is performed separately from the raw-bit profiles described below.
		\item During collection, every selected-bit observation is subjected to a Repetition Count Test with cutoff $C=51$ and a binary Adaptive Proportion Test with window $W=1024$ and cutoff $C=840$ in either bit direction.
		\item If either continuous health test fails, the partial entropy pool is destroyed. Each cached recovery candidate is revalidated against a fresh 1,024-read sample before activation; if none survives, the implementation performs at most one complete 513-address rescan for that collection attempt. Collection fails closed if no replacement qualifies.
		\item Physical TI-84+ CE hardware is expected to qualify reliably, whereas CEmu may fail because deterministic SRAM emulation does not reproduce the physical source.
		\end{itemize}
	
	\paragraph{Entropy Collection Model}
	The entropy collector prepares one 128-bit contribution via the following algorithm:
	\begin{itemize}
		\item Read the selected source byte 17 times for each of 119 entropy-pool bytes, XORing the reads into one composite byte.
		\item Apply the runtime repetition-count and adaptive-proportion health tests to every observation of the selected source bit.
		\item Hash the resulting 119-byte pool with SHA-256.
		\item Use the leftmost 128 digest bits as the conditioned contribution to the Hash\_DRBG entropy reserve.
	\end{itemize}
	
		The following \textbf{derived assumptions} apply:
		\begin{itemize}
			\item Entropy is credited only to the selected source bit; all other bits in each raw byte are treated as zero-entropy in the bound.
			\item Entropy is estimated at the raw selected tap. XOR and SHA-256 are deterministic conditioners and receive no independent entropy credit.
			\item The measured most-common-value estimate is marginal. Multiplying it by the number of observations is an engineering accounting model, not a formal non-IID entropy-rate proof; serial dependence can reduce the true joint min-entropy.
			\item A contribution is never credited with more than its 128-bit conditioned width, regardless of the raw accounting result.
			\item Runtime health checks are assumed to detect gross source failure, but short-window entropy collapse between checks remains a residual risk.
		\end{itemize}
		

	\subsubsection{Raw-Tap Min-Entropy Estimate}
	\label{ssec:min_entropy}
	The current profiler records eight tests of 32,768 selected raw bits per calculator, for 262,144 observations per profile. The checked-in reports are maintained directly in the repository's \href{https://github.com/cagscalclabs/lwip-ce/tree/master/statistics/rng}{\texttt{statistics/rng}} directory; this analysis does not depend on separately maintained appendix datasets.

	For each test, let
	\[
		\hat p_{\max}=\max\!\left(\frac{n_0}{n},\frac{n_1}{n}\right).
	\]
	The SP~800-90B MCV procedure's 99\% upper-confidence adjustment is recomputed from that test's own counts using its prescribed normal-approximation factor, $z=2.576$:
	\[
		\epsilon_{99}=2.576\sqrt{\frac{\hat p_{\max}(1-\hat p_{\max})}{n-1}},
		\qquad
		p_{\max,99}=\min(1,\hat p_{\max}+\epsilon_{99}).
	\]
	The plug-in and confidence-adjusted binary marginal MCV estimates are then
	\[
		\widehat H_\infty=-\log_2(\hat p_{\max}),
		\qquad
		H_{99}=-\log_2(p_{\max,99}).
	\]
	This adjustment is intentionally one-sided: only an upper bound on the most-common outcome probability produces the required lower bound on min-entropy. The same computation is repeated over the aggregate counts for each model rather than reusing a common margin of error.

	\IfFileExists{generated/rng_entropy_analysis.tex}{
		\input{generated/rng_entropy_analysis.tex}
	}{
		No generated RNG entropy analysis was found at build time.

	For each model, the working marginal estimate is the smaller of its aggregate lower bound and its worst individual-test lower bound:
	\[
		h_{\text{model}}=\min\!\left(H_{99,\mathrm{aggregate}},\ \min_i H_{99,i}\right).
	\]
	This prevents a long aggregate from hiding a weaker interval. Across calculator revisions, the implementation-level value is selected from the weakest measured model:
	\[
		h_{\text{all models}}=\min_m h_m=\RngOverallH\ \text{bits per raw selected-bit observation}.
	\]

	One collection performs $17\times119=2023$ selected-bit observations and emits a 128-bit conditioned contribution. Under the provisional additive-observation accounting model, the weakest measured model therefore gives
	\[
		H_{\text{raw,collection}}=2023h_{\text{all models}}=\RngOverallRawCollectionH\ \text{bits},
	\]
	The implementation rounds the measured cross-model value down to the configurable policy value $h_{\text{policy}}=0.35$, yielding $2023(0.35)=708.05$ provisionally accounted raw bits per collection. The contribution is then credited as
	\[
		H_{\text{credited}}=\min(128,2023h_{\text{policy}})=\RngOverallCredit\ \text{bits}.
	\]
	The 128-bit result is a credit cap imposed by the conditioned output width; it is not a claim that XOR or SHA-256 created entropy. More importantly, the reported MCV values characterize marginal bias only. Serial dependence can make joint min-entropy lower than $2023h$, so this multiplication and the configured working value remain conservative engineering policy supported by online health tests, not a complete SP~800-90B non-IID entropy assessment or certification. Post-conditioning measurements may test output quality, but they are not used to inflate the raw-source entropy estimate.
	
	\paragraph{Encapsulation}
	\label{ssec:encapsulation}
	
	Applications obtain random output through \texttt{tls\_random\_bytes()}, which is backed by SHA-256 Hash\_DRBG; the deprecated \texttt{tls\_random()} entry point is a compatibility wrapper over the same generator. Raw tap collection and conditioning are internal and cannot be requested through the public API.
	
	When the stack starts, it selects the SRAM tap and enables a 50\,ms entropy-collection dispatcher. Entropy-backed output can also be requested asynchronously through \texttt{tls\_request\_random\_bytes()}.
		\inputminted[
			breaklines,
			breakanywhere,
			fontsize=\footnotesize,
			firstline=153,
			lastline=153
		]{c}{../../src/tls/includes/random.h}
	This:
	\begin{itemize}
		\item Registers a request for random bytes, a buffer to return those bytes into, and a callback to run when the request completes.
		\item If \texttt{blocking=true}, execution halts only if instantiation or mandatory reseeding requires additional entropy.
		\item If \texttt{blocking=false}, execution returns to the caller immediately; the callback function fires when the request is fulfilled.
	\end{itemize}
	
		The timer fills a 256-bit entropy reserve in 16-byte conditioned steps. On each active collection cycle, the RNG path behaves as follows:
		\begin{itemize}
			\item The assembly collector reads the selected SRAM tap, applying the repetition-count and adaptive-proportion tests to every selected-bit observation.
			\item Seventeen raw byte reads are XOR-conditioned into each of 119 pool bytes; SHA-256 then conditions the pool, and its leftmost 16 bytes form one contribution.
			\item The contribution receives at most 128 bits of entropy credit, bounded by the configured conservative raw-source min-entropy estimate.
			\item At 256 credited bits, an uninstantiated generator is instantiated. Otherwise the complete reserve is retained and incorporated by the next Hash\_DRBG reseed.
			\item Once instantiated, Hash\_DRBG output does not consume entropy credit one-for-one. The timer replenishes the reseed reserve independently and stops while that reserve is full.
		\end{itemize}
		In blocking mode, \texttt{tls\_request\_random\_bytes()} performs only entropy work required for initial instantiation or mandatory reseeding. In non-blocking mode, requests are queued and completed by the dispatcher.
		
		If quick statistical testing demonstrates that the source has degraded beyond acceptable levels, the generator initialization function is called, which should cause a new source to be selected. Given the abstraction between tap, the entropy pool, and the DRBG, choosing a new entropy tap is invisible and does not impact upstream state.

	\subsection{Certificate Chain Trust Model}
	A core requirement for Internet security is authenticating that the remote endpoint is actually the party it claims to be. In TLS, that assurance is normally derived from certificate-chain validation against a trust anchor.
	
	On this platform, however, certificate handling introduces three practical constraints:
	\begin{itemize}
		\item Certificate chains can be large (often multiple kilobytes), which is expensive relative to available heap.
		\item Full-path X.509 processing and repeated signature checks are computationally heavy on the CE.
		\item As with the RNG capture constraints discussed earlier, the CE does not have sufficient storage budget for a desktop-scale trust store.
	\end{itemize}
	We needed a trust model that remained defensible for the intended use case while still allowing the calculator to complete a handshake without experiencing a nuclear meltdown in its CPU. The model combines two independent checks: \emph{adjacent-link} chain signature verification across the presented \texttt{Certificate} message, and the mandatory TLS 1.3 \texttt{CertificateVerify} check for live proof-of-possession of the leaf key. This approach is intentionally narrower than a full desktop-class WebPKI verifier: the tradeoff is reduced processing and memory pressure in exchange for an explicit, bounded trust boundary.

	\paragraph{CertificateVerify}
	Chain verification establishes that the certificates link together cryptographically, but it does not on its own prove that the entity we are speaking with controls the leaf private key. A network attacker holding only the leaf certificate---which is public---would otherwise pass a structural check. TLS 1.3's \texttt{CertificateVerify} message closes that gap: the server signs a digest of the handshake transcript with its leaf private key. We require this message and verify it on every full handshake.

	The implementation is restricted to \texttt{rsa\_pss\_rsae\_sha256} with a leaf RSA modulus between 1024 and 2048 bits. Servers selecting \texttt{ecdsa\_secp256r1\_sha256}, the wider RSA-PSS hash variants, or RSA-PKCS1 (which RFC~8446 §4.4.3 forbids in \texttt{CertificateVerify} regardless) are rejected with a fatal \texttt{decrypt\_error} alert. Support for \texttt{ecdsa\_secp256r1\_sha256} and RSA keys up to 4096 bits is planned.

	\paragraph{CertificateRequest}
	A server may ask the client to authenticate with its own certificate. Client certificates are currently out of scope for this implementation, but the request still has to be handled correctly: \texttt{CertificateRequest} participates in the handshake transcript that both sides' \texttt{Finished} MACs are computed over, so it cannot simply be ignored. The handshake parser validates the message's nested request-context and extension-list lengths, feeds the exact bytes into the transcript hash, and records that the server asked (\texttt{client\_certificate\_requested}). Rather than aborting or omitting the response, the client replies with an empty \texttt{Certificate} message (a zero-length certificate list, per RFC~8446 §4.4.2) and no \texttt{CertificateVerify}, which is the standard, spec-compliant way to decline client authentication while keeping the transcript---and therefore the handshake---valid.

	\paragraph{Certificate Chain Parsing and Adjacent-Link Verification}
	When operating as a client, the implementation streams the TLS \texttt{Certificate} message one certificate at a time rather than buffering the whole chain, and verifies each \emph{link} against the next certificate's public key. Because certificate $N$ is signed by certificate $N{+}1$, and $N{+}1$ has not yet arrived when $N$ finishes parsing, the walker defers: it holds $N$'s signature material until $N{+}1$ arrives, then verifies the pending link with $N{+}1$'s key.
	\begin{itemize}
		\item An \texttt{RSA-2048} link signed with \texttt{sha256WithRSAEncryption} is verified for real (PKCS\#1~v1.5, SHA-256). A signature that fails to verify is fatal: the handshake is aborted (an \texttt{ERROR}-severity diagnostic is emitted).
		\item Any other signature type---\texttt{ecdsa\_secp256r1\_sha256}, wider RSA-PSS hashes, or a non-RSA issuer key the link cannot be checked against---is \emph{not} verified. The link is accepted and the stack raises an \texttt{ALERT(unsupported algorithm, PASS)} so the application can observe that the link went cryptographically unchecked.
		\item The topmost certificate has no issuer within the presented chain, so its issuer is looked up in the on-device truststore by subject name. If found and RSA (PKCS\#1~v1.5 or PSS, SHA-256), the root link is verified for real with the same fatal-on-failure treatment as an adjacent in-chain link. If the issuer is absent from the truststore, or uses a signature type not yet supported (e.g. ECDSA), the chain is accepted with \texttt{ALERT(root not in store, PASS)}.
	\end{itemize}
	The \texttt{WARN-PROCEED} is an interim posture only intended until gaps in our signature algorithm support are closed.

	\paragraph{Hostname and Validity-Period Checks}
	Chain-link signatures and \texttt{CertificateVerify} together establish that the presented chain is internally consistent and that the peer holds the leaf private key --- but neither one proves the leaf certificate was actually issued for the host the client meant to connect to, nor that it is currently within its issuer-stated validity period. Both gaps are closed as part of the same per-certificate pass that runs the adjacent-link check above, fail-closed on either:
	\begin{itemize}
		\item \textbf{Hostname/SAN matching} (leaf only): the leaf certificate's \texttt{subjectAltName} extension is walked for \texttt{dNSName} entries and compared against the hostname supplied in the client's own SNI \texttt{ClientHello} extension, including a single leading-label wildcard (\texttt{*.example.com} matches \texttt{foo.example.com} but not \texttt{example.com} itself or a deeper sub-label). If the leaf has no \texttt{subjectAltName} extension at all, the check falls back to the subject CommonName, per RFC~6125 \S6.4.4; if a \texttt{subjectAltName} is present, the CommonName is never consulted, even if none of its \texttt{dNSName} entries match. A leaf that doesn't match the connection hostname aborts the handshake before \texttt{CertificateVerify} is even reached.
		\item \textbf{Validity-period enforcement} (every certificate in the chain): each certificate's \texttt{notBefore}/\texttt{notAfter} fields are parsed (UTCTime and GeneralizedTime are both supported) and checked against the device's current time. An expired or not-yet-valid certificate anywhere in the chain --- leaf, intermediate, or the truststore-anchored root --- aborts the handshake, not just the leaf.
	\end{itemize}
	The device has no guaranteed accurate clock source independent of the network it's trying to secure: the on-device RTC is reset to an arbitrary value by a RAM clear and is not otherwise synchronized until an application performs SNTP. To keep validity-period enforcement meaningful even before SNTP has ever run, the RTC is clamped forward at stack-init time to a fixed, manually-updated ``minimum plausible clock'' floor (a recent library release date) whenever it reads earlier than that floor. This rules out the degenerate case where every certificate in the world appears valid because the device's clock reads 1970, without requiring a working network path before TLS can be used at all. It is a plausibility floor, not an accuracy guarantee --- a clock that has drifted forward of the floor is not corrected by this mechanism, only one that has fallen behind it.

	The handshake therefore completes when every RSA link it could verify---including the root anchoring check---did verify, no verifiable link failed, every certificate's validity period covers the current device time, the leaf certificate matches the connection hostname, and the leaf's \texttt{CertificateVerify} signature checks out. The on-device truststore format is specified in the next section.

	\subsection{Trust Store Generation and Specification}

	\paragraph{Generation}
	The truststore is generated by a scheduled GitHub Actions workflow (quarterly) and published as a signed TI AppVar (\texttt{.8xv}) for device deployment. Conceptually, it serves the same role as an OS trust-anchor bundle, but in a compact, platform-specific format.
	The \texttt{Store Version} field is a binary schema compatibility contract, not a content revision marker. It is incremented only when serialization/parsing semantics change in a way that affects decoding. Routine truststore content updates, naming changes, and signer-key rotation do not require a version increment.

	The workflow:
	\begin{enumerate}
		\item Scans common CA-certificate locations on the runner (for example \texttt{/etc/ssl/certs}) and collects parseable trust anchors.
		\item Extracts the following from each certificate, skipping any whose key the device-side verifier cannot handle (RSA moduli above the supported size, or non-P-256 EC keys):
		\begin{itemize}
			\item The subject common name (CN) and the \texttt{SubjectKeyIdentifier} extension, used at lookup time to anchor a chain's topmost certificate to its issuer by subject-name match
			\item The expiry timestamps (not-before, not-after)
			\item The signature algorithm class (RSA-PSS/SHA-256, RSA-PKCS\#1~v1.5/SHA-256, or ECDSA-P-256/SHA-256), recorded as a compact internal code rather than an ASN.1 OID
			\item The raw public key material used by the root-anchoring RSA verification described above
		\end{itemize}
		\item Serializes a binary truststore with the following layout. Per-entry records are variable-length (the trailing key field's size depends on the key type), so each is length-prefixed rather than fixed-size:
		\begin{figure}[H]
			\centering
			\scriptsize
			\rowcolors{2}{ltgray}{white}
			\begin{tabularx}{0.92\textwidth}{@{}>{\raggedright\arraybackslash}X>{\centering\arraybackslash}m{2.4cm}>{\raggedright\arraybackslash}X@{}}
				\toprule
				\rowcolor{gray!18}
				Field & Size & Notes \\
				\midrule
				Signature Field & 256 bytes & RSA-2048 PSS-SHA-256 signature over the header fields below plus all entries \\
				Store Version & 2 bytes & Truststore schema version \\
				Created Timestamp & 4 bytes & Build timestamp \\
				Entry Count & 2 bytes & Number of certificate records \\
				\rowcolor{gray!22}
				\multicolumn{3}{@{}l@{}}{\textbf{Per-certificate record (repeated \texttt{Entry Count} times, variable length)}} \\
				Entry Length & 4 bytes & Total byte size of this record, including the key field \\
				Subject & 32 bytes & Subject CN, null-terminated and padded \\
				Subject Key Identifier & 32 bytes & SKI extension bytes, padded \\
				Not-Before & 4 bytes & Validity start timestamp \\
				Not-After & 4 bytes & Validity end timestamp \\
				Algorithm Id & 1 byte & RSA-PSS, RSA-PKCS\#1~v1.5, or ECDSA-P-256 \\
				Key & variable & Raw public key: RSA exponent+modulus, or an EC point \\
				\bottomrule
			\end{tabularx}

		\item Signs the truststore bytes from \texttt{Store Version} through \texttt{EOF} using RSA-2048 PSS-SHA-256 and writes the signature into \texttt{Signature Field}.
		\item Stores the signing key in GitHub Secrets, materializes it only in runner temp storage for signing/verification, then deletes it (including \texttt{shred} cleanup).
		\item Converts the binary store to TI AppVar format (\texttt{.8xv}) via \texttt{convbin}.
		\item Publishes the resulting AppVar, named \texttt{lwIPCERT.8xv} on-device, under the \texttt{truststore-latest} release tag.
		\item Links validation at runtime by shipping the corresponding public verification key within lwIP's truststore module.
	\end{enumerate}
	
A truststore age check (warning only, not a rejection condition, comparing \texttt{created\_timestamp} against a threshold once time can be trusted via a valid local clock or NTP) is planned but not yet implemented; the on-device truststore currently carries no age-based behavior at all.
	
	Algorithm agility is version-gated. The current format uses RSA-2048 PSS-SHA-256 for truststore signatures; future signature-scheme migrations are expected to ship behind an explicit format/version transition plus corresponding verifier update.

	\paragraph{Runtime Initialization}
	When the network layer comes up, it also initializes the truststore, which performs (1) signature verification of the truststore against the embedded public verification key, and (2) schema/version compatibility checks against the version expected by lwIP. Truststore initialization failure does not block TLS connections outright: it degrades gracefully to the same posture as an absent truststore, leaving root anchoring unavailable for that session (the adjacent-link and \texttt{CertificateVerify} checks described above are unaffected and still run). A chain whose topmost issuer would otherwise have been anchored is instead accepted with an \texttt{ALERT}-severity diagnostic, the same fallback used for any issuer absent from a valid store.

	\paragraph{Compromise and Revocation}
	If the truststore signing key is suspected or confirmed compromised, the incident response is:
	\begin{enumerate}
		\item Revoke and replace the compromised signing key.
		\item Regenerate the truststore under the replacement key.
		\item Publish a new lwIP release embedding the replacement public verification key.
		\item Publish a security advisory across project channels (GitHub, Discord, and community forums).
	\end{enumerate}

	\subsection{Profiling}\label{ssec:profiling}

	Alongside the stack-wide unit tests described in Section~\ref{ssec:profiling_unit_tests_ref}, this section covers the TLS-specific, profiling-oriented validation layer. Where unit tests verify functional correctness, safety checks, and regression resistance for module behavior, profiling tests characterize timing stability, performance behavior, and platform-dependent variance under controlled workloads.

	Profiling tests are intentionally separated from strict correctness gating. Their role is to quantify behavior, not merely assert it. In particular, timing-oriented tests evaluate differential behavior across input classes and report whether observed variance remains within calibrated bounds. Because timing consistency evidence is environment-sensitive, profiling outcomes are interpreted as indicators and trend signals rather than formal proofs.
	
	\subsubsection{Timing Analysis Profiler}
	The primary profiling module, \texttt{tls\_timing}, uses robust per-primitive calibration instead of a fixed global cycle limit. For each primitive, repeated samples are collected on a calibration class (``same input'', currently the best-case class), yielding cycle samples $\{T_1,\dots,T_n\}$. The following robust statistics are then computed:
	
	\begin{align*}
		m &= \operatorname{median}(T_1,\dots,T_n),\\
		\operatorname{MAD} &= \operatorname{median}\left(\left|T_i - m\right|\right),\\
		\sigma_{\text{robust}} &= 1.4826 \cdot \operatorname{MAD}.
	\end{align*}
	
	For each tuning constant $c$, the accepted cycle deviation is:
	\begin{align*}
		\Delta_c = \max\!\left(c,\; c\cdot \sigma_{\text{robust}}\right).
	\end{align*}
	
	Two $c$ modes are reported for every primitive:
	\begin{itemize}
		\item \textbf{Standard mode}: $c=6$ (used for pass/fail gating in CI).
		\item \textbf{Rigorous mode}: $c=4$ (reported for additional strictness, not current gate criterion).
	\end{itemize}
	
	Each primitive is then evaluated across input classes (best, worst, random, edge), defined:
	\begin{itemize}
		\item \textbf{Best-Case}: Input is filled with $0x00$.
		\item \textbf{Worst-Case}: Input is filled with $0xFF$.
		\item \textbf{Random}: Input is filled with pseudo-randomness.
		\item \textbf{Edge-Case}: First half of the input is filled with $0x00$ and the second half is filled with $0xFF$.
	\end{itemize}
	
	For each class, the reported statistics include class median deviation from the calibration median and exceedance rate (percentage of samples where $|T_i-m|>\Delta_c$). A differential failure is flagged when separation from calibration exceeds the accepted deviation with directionally consistent behavior across at least a three-quarters majority of samples.	
	
	Each unit is sampled $32$ times, where each sample is a composite of repeated executions selected by algorithm runtime class: fast units use $4$ repetitions, medium units use $2$, and slow units use $1$. This batching further suppresses class-independent timing jitter.

	Latest timing-profiler workflow results: \url{https://github.com/cagscalclabs/lwip-ce/actions/workflows/timing.yml}.

	\subsubsection{CAVP Validation}

	Formal cryptographic certification depends not only on algorithm behavior, but also on implementation context, build process, operating environment, and hardware security properties. Because this stack runs as calculator application code on hardware without a secure execution environment or certified key-storage boundary, it is not presented as a formally certified cryptographic module.

	
	Instead, the project demonstrates algorithmic correctness against NIST CAVP-published response files and compatible generated reference vectors. The CAVP workflow downloads the relevant NIST \texttt{.rsp} vector archives for supported primitives and selects 16 random samples per primitive on each run. For primitives without compatible CAVP response files, vectors are generated during the workflow with \texttt{python3-cryptography} using the relevant RFC-defined algorithm parameters. If NIST resources are unavailable, the workflow uses the cached CAVP archives from a previous successful run; if neither the source archive nor cache is available, validation fails closed.

	\paragraph{Round-trip pipeline}: The reason for the AppVar hand-off is that the implementation under test only exists on the calculator --- the same eZ80 binary that ships, not a host re-build --- so the vectors have to travel to the device and the answers have to travel back. The pipeline has four stages. \emph{(1) Serialization}: the host harness encodes the selected vectors (inputs, keys, IVs, and the metadata identifying which primitive and operation each belongs to) into the \texttt{CAVPIN} AppVar, a flat binary layout the on-device runner can walk without a parser. \emph{(2) On-device execution}: \texttt{CAVPIN} is loaded onto the emulator, the runner reads each record, calls the real lwIP-CE implementation, and appends the computed output to the \texttt{CAVPOUT} AppVar --- the device never sees the expected answers, so it cannot accidentally echo them. \emph{(3) Exfiltration}: \texttt{CAVPOUT} is pulled back off the emulator to the host. \emph{(4) Comparison}: the host parses \texttt{CAVPOUT} and checks each computed value against the reference output it withheld in stage~1, byte-for-byte. A mismatch on any sample fails the run and names the offending primitive and vector index, so a regression points at a specific algorithm rather than a vague ``CAVP failed.'' Keeping the reference answers exclusively on the host side is deliberate: it ensures the device is genuinely computing the result, not transporting it.

	\paragraph{Exclusions}: RSA-PSS vectors are generated with \texttt{python3-cryptography} because this implementation fixes $e=65537$, while the available NIST PSS response files do not provide a compatible fixed-exponent set. X25519 vectors are also generated with \texttt{python3-cryptography}, supplemented by RFC 7748 vectors, because CAVP does not publish X25519 coverage for this use case.

	Latest CAVP-validation workflow results: \url{https://github.com/cagscalclabs/lwip-ce/actions/workflows/cavp.yml}.

	\subsection{Profiling and Mitigating Platform Security Limitations}
	
	\subsubsection{The TI-84+ CE Hardware Security Profile}
	The threat model above treats local and physical attackers as out of scope because the TI-84+ CE lacks the hardware primitives normally used to defend against them. This section identifies the platform limits that shape that decision and the narrow mitigations implemented anyway.
	
	\textbf{Profile Characteristics}
	\begin{itemize}
		\item The platform is built around a Zilog eZ80-class CPU (24-bit addressing mode, 48\,MHz class operation), optimized for calculator workloads rather than secure key custody or trusted execution.\footnote{\url{https://ce-programming.github.io/toolchain/static/hardware.html}}
		\item There is no hardware secure enclave, TPM-equivalent, MMU-backed isolation boundary, or dedicated primitive for sealing long-term private key material in user-space workflows.
		\item Memory and storage interfaces are observable and modifiable by a sufficiently privileged local tool or a user with physical control of the device and transfer path.
		\item Runtime checks that depend on wall-clock time (for example certificate validity windows or truststore age warnings) are only as reliable as the device clock state or external synchronization path.
	\end{itemize}
	
	Software cannot close those gaps, but it can reduce avoidable exposure. lwIP-CE therefore focuses its local hardening on two practical targets: limiting host-assisted observation during active cryptographic transforms and reducing residual plaintext/key material left in stack or heap buffers after use. These mechanisms are implemented through the \textbf{cryptoguard} wrapper and explicit zeroization paths described below.
	
	\subsubsection{Cryptoguard Wrapper}
	The \texttt{cryptoguard} module wraps security-sensitive routines with two best-effort protections:
	\begin{itemize}
		\item Saves the current interrupt state, then disables system interrupts. This reduces the opportunity for host-assisted observation during sensitive operations, since USB activity handling depends on interrupt-driven processing. On exit, the prior interrupt state is restored.
		\item Clears stack memory from the current stack location up to the configured stack top before returning to the caller. This reduces residual exposure of stack-allocated buffers and intermediate values after sensitive routines complete.
	\end{itemize}

\textbf{Additional Implemented Security Mechanisms}
\begin{itemize}
	\item \texttt{tls\_secure\_memzero()}: A secure zeroization routine intended to avoid compiler elimination of memory-clearing operations. Unlike a plain \texttt{memset()}, it uses \texttt{volatile}-qualified access so clearing side effects are preserved during optimization.
	\item \textbf{Secure Membuffer Contexts}: As noted in the allocator section, a \texttt{membuffer} created with \texttt{BUFFER\_\allowbreak SECURE\_\allowbreak MODE} applies automatic zeroization in key lifecycle paths:
	\begin{itemize}
		\item when \texttt{free()} is called on pool-allocated blocks;
		\item when bytes are popped from a ring buffer;
		\item in dynamic mode, when the allocation shrinks (the released region is zeroed).
	\end{itemize}
\end{itemize}

When evaluated in unison, these mechanisms provide best-effort memory sanitization across allocation, use, and teardown paths, reducing residual plaintext/key exposure without claiming complete protection against a local or physical adversary.

		\section{Conclusion}
		This work demonstrates that a modern TCP/IP stack with TLS support can be adapted to the TI-84+ CE class of hardware when the design is shaped around the platform rather than merely compressed to fit it. More broadly, it is an existence proof for a class of device most would write off entirely: a single-core processor in the low tens of megahertz, with no MMU, no hardware cryptographic acceleration, no secure element, and a memory budget measured in kilobytes can still host an interoperable TLS~1.3 client against the live internet --- provided the constraints are treated as first-class design inputs rather than obstacles to paper over. The resulting system combines USB CDC Ethernet transport, lwIP protocol handling, memory-pressure-aware buffering, a resident application call model, and a constrained TLS 1.3 implementation into a coherent network stack for a device with severe memory, timing, and security limitations.
		
		The central engineering result is not that the TI-84+ CE can be made equivalent to a desktop or server environment. It cannot. The platform lacks a hardware root of trust, secure key storage, preemptive multitasking, and the memory budget normally assumed by contemporary networking and cryptographic software. The relevant result is narrower and more useful: with explicit boundaries, conservative assumptions, and targeted validation, the platform can support interoperable secure-client workflows and provide a practical foundation for calculator-native networked applications.
		
		Several design choices carry that result. The USB Ethernet driver limits scope to CDC ECM/NCM behavior that can be made reliable on the device. The membuffer layer makes allocation pressure visible and gives ingress paths a way to degrade predictably. The RNG model treats the hardware entropy source as something to be measured, conditioned, and health-checked rather than assumed. The truststore design replaces desktop-scale WebPKI expectations with a signed, compact, platform-specific trust boundary. The TLS implementation and profiling suite then build on those constraints with explicit tests, timing telemetry, and failure behavior.

		The four self-audit workflows described in this document --- deterministic unit testing, CAVP-vector validation, differential timing analysis, and static analysis (SAST) --- are not isolated test jobs but a single, deliberately layered \emph{pre-audit validation pipeline}. Unit testing establishes functional correctness and fail-closed behavior against RFC- and CAVP-derived vectors; CAVP validation independently confirms that the shipping on-device binary computes standard algorithm outputs correctly, end to end; differential timing analysis characterizes the constant-time properties that functional tests cannot see; and SAST (Semgrep) statically scans the project's own additions against upstream lwIP for unsafe patterns, so review attention is focused on changed code rather than the inherited base. Each runs on every push and emits a self-contained, source-independent job summary. Collectively they are intended to do the preparatory work a formal third-party audit would otherwise start from scratch: they make the project's correctness, timing, and code-quality claims continuously reproducible, machine-checked, and legible to an external reviewer, so that an audit can begin from evidence rather than assertion. That this depth of standing validation is achievable on a calculator is itself part of the result.

	\subsection{Community Data Contributions}
	\label{ssec:contributing_data}

	Two of the analyses in this document --- the raw-tap entropy characterization in Section~\ref{ssec:min_entropy} and the differential timing characterization above --- benefit materially from broader hardware coverage than any individual developer can produce. The TI-84+ CE has gone through several hardware revisions over its production lifetime, and physical-source behavior (in particular the SRAM bitline characteristics underlying the entropy tap) is not guaranteed to be uniform across them. Community-contributed captures expand the empirical envelope rather than re-validate the existing bound: each submission adds coverage for a device class the project's own benches do not include.

	\paragraph{What to capture}
	Two on-device tools produce the submission artifacts:
	\begin{itemize}
		\item \textbf{RNG tap profile.} The profiling application records eight windows of 32,768 observations from the exact selected source bit used by the runtime collector. Its companion analyzer recomputes the per-window and aggregate MCV estimates and writes a uniquely named JSON or CSV report to \texttt{statistics/rng}. Submissions should identify the calculator model so results can be grouped by hardware revision.
		\item \textbf{Differential timing capture.} Produces a structured log file using a \texttt{key=value} record format. Each unit's calibration class and per-class results are emitted with explicit denotation so the upstream analysis can locate each unit and its associated measurements by regular expression. The log can be exfiltrated via standard AppVar transfer.
	\end{itemize}

	\paragraph{Device identification}\label{par:device_id}
	Contributions are most useful when accompanied by enough device metadata to locate the submission within the broader sample population. At minimum:
	\begin{itemize}
		\item Hardware revision (visible on the back-label sticker or via \texttt{[mode]} $\rightarrow$ \texttt{[about]}).
		\item Operating system version.
		\item Boot code version, where reported by the device.
	\end{itemize}
	Contributors who are unsure which revision they hold are encouraged to submit anyway with whatever metadata they can identify; the project can usually disambiguate from the supplied OS and boot-code strings.

	\paragraph{Issue tracebacks}\label{par:issue_tracebacks}
	The known and outstanding issues tracked in Appendix~\ref{ssec:known_issues} (notably \texttt{st closed sent 0}/\texttt{st closed sent 1}) are presently blocked on field reproduction data rather than RNG or timing coverage, and benefit from the same submission channels. A useful traceback report includes:
	\begin{itemize}
		\item \textbf{Traceback output.} The v1.0-rc4 traceback system's captured output at the point of failure (see Section~\ref{ssec:engineering_notes}), including the state string (e.g.\ \texttt{st closed sent 0}) and any preceding trace lines, not just the final line.
		\item \textbf{Peer/server identity.} The hostname or service the connection was made to, and, if known, the TLS server implementation (e.g.\ nginx, a specific embedded TLS stack) --- the suspected cause is a missing or misinterpreted record type from certain peers.
		\item \textbf{Reproducibility.} Whether the failure is consistent against that peer or intermittent, and approximately how far into the post-handshake exchange it occurs.
		\item \textbf{Build/version.} The lwIP-CE library version and, where applicable, the calling application's version, since trampoline and record-handling behavior can shift between revisions.
		\item \textbf{Device metadata.} The same hardware revision, OS version, and boot code requested under \nameref{par:device_id} above, in case the failure correlates with a hardware or firmware class.
	\end{itemize}
	As with calibration captures, tracebacks carry no submitter-identifying metadata by default and are evaluated purely on their technical content.

	Submissions can be sent via either channel below:
	\begin{itemize}
		\item Project Discord: \url{https://discord.gg/CtEq3rXZGJ} --- a dedicated channel exists for capture submissions and questions about the protocol.
		\item Direct email: \texttt{info@cagscalclabs.net} --- preferred when attaching large AppVar bundles.
	\end{itemize}
	The capture tool itself, its source, and the parsing scripts are versioned within this repository; contributors are asked to record which tool version produced their submission so the analysis pipeline can account for any schema changes between releases.

	\paragraph{Privacy and licensing}

	\subsection{Differential Timing Analysis Dumps}
	
	The differential timing profiler is a robust timing-assessment tool designed to verify that no input class for a unit exhibits detectable runtime drift beyond a class-independent jitter model. As described in the main text, it estimates $\sigma$ and derives both standard and strict cycle-deviation thresholds from variance measured in the best-case class.
	
	The tables below report per-unit averaged statistics by model. Each row is shaded green when the unit passes and red when it fails under the profiler criterion (directionally consistent runtime deviation above threshold at least 75\% of the time). For release-quality builds, all rows should be green.

	\paragraph{What ``good'' looks like}: a passing unit shows a small \textbf{Avg $\sigma$} (low intrinsic jitter in the calibration class), \textbf{MedDev (W/R/E)} values close to zero for all three input classes --- worst-case (W), random (R), and edge (E) --- meaning no class runs systematically faster or slower than the others, and \textbf{Over\%} entries at or near $0\%$, indicating that few or no samples exceeded the cycle-deviation threshold. The \textbf{Avg $\Delta$ (c6/c4)} column reports the calibrated standard/strict thresholds themselves and is contextual rather than pass/fail. A failing unit is the inverse: a non-trivial MedDev that points the same direction across most samples, paired with a high Over\%, which is the signature of input-dependent timing the profiler is built to surface.

	\paragraph{A note on per-model sample size}: each table's footer reports how many source files were parsed for that model, and this varies considerably by revision (the project's own bench coverage is uneven across hardware classes). A model represented by only one or two captures gives a single run's jitter outsized weight in \textbf{Avg $\sigma$} and \textbf{Avg $\Delta$}, so an isolated high reading on a thinly-sampled model --- as opposed to a reading that recurs across multiple runs or models --- is more plausibly a small-sample artifact than a genuine platform-specific timing characteristic, and should be read with that caveat rather than as a confirmed anomaly.

	\subsection{Cryptographic Primitive Security Properties}\label{ssec:crypto_properties}

	Per-primitive security property matrix. \textbf{\checkmark} = confirmed. \textbf{\texttimes} = not present or not verified. \textbf{?} = unknown / unverified. Current profiling has identified timing variation only over public quantities; no private-key or session-secret material is intentionally used in timing-dependent paths.

	\begin{description}[leftmargin=0pt,labelwidth=\widthof{\textbf{Cache Safe: }},align=left,nosep]
		\item[\textbf{CT:}] Verified constant-time (within acceptable margin of jitter) for the core primitive.
		\item[\textbf{Zeroed:}] All scratch buffers, allocations, and stack memory purged upon release.
		\item[\textbf{IRQ-Gated:}] Function runs with system interrupts disabled to inhibit side-loading via USB.
		\item[\textbf{CT Tag Cmp:}] Authentication tag or MAC comparison performed without early exit.
		\item[\textbf{Cache Safe:}] Flash cache timing analysis. Applies to Rev~M or later hardware, which introduced a flash read cache.
	\end{description}
